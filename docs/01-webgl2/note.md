## 진화 1 사전 학습 — 셰이더 개념 깨달음 기록

**1. "fragment가 삼각형 아니었나?" — vertex / primitive / fragment 세 단위의 분리**

fragment를 삼각형이라고 잘못 알고 있었다. 정리: **vertex**(숫자 묶음을 가진 정점 하나) → **primitive**(정점들을 엮은 도형 — 삼각형·선·점) → **fragment**(primitive가 덮은 **픽셀 자리 하나**에 대한 색칠 후보). 파이프라인이 vertex shader → 래스터화 → fragment shader 순서인 이유: 도형이 어떤 픽셀을 덮는지 계산하려면(래스터화) 먼저 도형의 화면 위치가 확정돼야 하기 때문. 래스터화가 데이터의 단위를 정점에서 픽셀 자리로 바꾸므로, 실행 횟수도 다르다 (8×8 점 하나 = vertex 1번, fragment ~64번).

**2. "정점 = 삼각형의 꼭짓점"이라는 오해 — 정점의 정체는 draw call이 정한다**

정점이 본질적으로 삼각형의 꼭짓점이라고 생각했는데, 반만 맞다. 세상의 3D는 대부분 삼각형 메시라 통계적으론 그렇지만, 정점 자체는 그냥 숫자 묶음이고 **`drawArrays`의 첫 인자(`gl.TRIANGLES`/`gl.LINES`/`gl.POINTS`)가 같은 정점들을 뭐로 엮을지 정한다.** vertex shader는 자기가 삼각형의 일부인지 점인지 모른 채 똑같이 실행된다. 내 파티클 프로젝트에선 `gl.POINTS` — **정점 1개 = 파티클 1개**, 삼각형은 진화 3에서 만난다.

**3. 흐르는 데이터의 실체 — 전부 평평한 실수 나열이다**

buffer는 `[x0,y0,x1,y1,...]`이라는 그냥 float 나열(점 3개 = 실수 6개 = 24바이트)이고, 그 안에 "점"이라는 구조는 없다. "2개씩 잘라 한 정점 몫"이라는 해석은 내가 `vertexAttribPointer`(JS 쪽)와 `in vec2`(GLSL 쪽)로 선언하는 것이며, **두 선언이 어긋나도 에러가 안 나고 조용히 이상한 값이 흐른다.** uniform도 실수 몇 개, 최종 출력도 픽셀당 RGBA 4바이트. 전 과정이 숫자의 나열 + 해석의 약속이다.

**4. 좌표는 픽셀이 아니다 — clip space라는 해상도 무관 좌표**

`gl_Position`에 넣는 좌표는 픽셀(정수 격자, 캔버스 크기 종속)이 아니라 **clip space: -1~1의 연속 실수, 해상도 무관**. `(0,0)`이 정중앙. 픽셀로의 변환(`픽셀x = (clipX+1)/2 × 폭`)은 래스터화 때 GPU가 viewport 설정 기준으로 자동 수행한다. 캔버스 크기가 바뀌어도 buffer를 다시 만들 필요가 없는 이유.

**5. 입출력의 비대칭 — 입력은 자유, 출력은 고정 계약**

vertex shader의 입력(attribute)은 "아무 숫자나"다 — 위치든 속도든 색이든 GPU는 의미를 모르고, 의미는 내 셰이더 코드가 부여한다. 반면 출력은 **clip space vec4 `gl_Position`으로 고정**이다. 이유: 다음 단계(래스터화)가 프로그래밍 불가능한 고정 하드웨어라 입력 형식을 협상할 수 없다. fragment shader도 동일 구조(입력 자유, 출력은 `out vec4` 색). 단 입력의 "자유"는 **의미의 자유**일 뿐, 형식은 규격이다: 숫자만, 정점마다 고정 크기, attribute당 최대 4성분(vec4), 슬롯 최소 보장 16개.

**6. 계약 준수는 온전히 개발자 책임이고, 어겨도 조용하다**

타입(vec4인지)은 컴파일러가 잡아주지만, **값의 의미(-1~1 범위의 진짜 clip space인지)는 아무도 검사하지 않는다.** 픽셀 감각으로 `(400, 300)`을 넣어도 합법 — 전부 클리핑돼 조용한 빈 화면이 될 뿐. 예외도 스택트레이스도 없으므로, 그래픽스 디버깅은 도구가 아니라 **원인을 이분법으로 좁히는 진단 순서**(clear 되나 → 컴파일 로그 깨끗한가 → 좌표 범위는…)로 한다.
