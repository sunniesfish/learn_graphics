# 공통 토대 (foundations)

진화와 무관하게 4번 다 관통하는 멘탈모델. **진화 1 시작 전에 한 번**, 그리고 **막힐 때마다** 돌아올 문서다. API 문법은 안 다룬다 — 그건 [roadmap.md](roadmap.md)가 링크한 정본(WebGL2 Fundamentals 등)의 몫이고, 여기선 그 정본을 **더 빨리 읽게 해줄 골격**만 준다.

> 튜터 모드: 이 문서는 개념과 멘탈모델만 다룬다. 네가 진화마다 직접 짤 해답 코드는 여기에도, concept.md에도 없다.

---

## 1. 딱 하나만 기억한다면: 방향이 반대다

네 FaceRGB 경험은 **GPU → CPU (readback)** 방향이었다. 프레임버퍼/텍스처에서 픽셀을 다시 읽어와 CPU에서 신호처리했지. 그 왕복의 비용·동기화·비동기 함정을 몸으로 안다.

그래픽스 렌더링은 그 **정반대 방향**이다:

```
CPU (JS 배열)  →  GPU 메모리 (buffer)  →  셰이더가 병렬 처리  →  화면
```

readback을 "피하고 싶은 비싼 것"으로 알던 감각이, 여기선 **"데이터를 GPU에 올려두고 CPU로 다시 안 내리는 게 이상적"** 이라는 감각으로 뒤집힌다. 진화 4의 compute shader가 이 뒤집힘의 정점이다 — 시뮬레이션을 통째로 GPU 안에 가둬서 readback을 아예 없앤다. 네가 배치로 왕복을 줄이던 그 문제를, 여기선 왕복 자체를 삭제한다.

이 한 문장을 붙잡고 있으면 나머지가 다 이 축에 걸린다.

## 2. 렌더링 파이프라인: 데이터가 화면이 되기까지

점 하나가 화면 픽셀이 되기까지 거치는 컨베이어 벨트. 네가 제어하는 두 칸(★)이 셰이더다.

```
정점 데이터(buffer)
      │  attribute로 정점별로 꺼내짐
      ▼
[★ Vertex Shader]   ← 정점 1개당 1번 실행. "이 점이 화면 어디에?" → gl_Position
      │
      ▼
Rasterization       ← 도형을 픽셀(fragment) 후보들로 쪼갬. GPU 고정 기능, 네가 못 건드림.
      │
      ▼
[★ Fragment Shader] ← 픽셀 후보 1개당 1번 실행. "이 픽셀 무슨 색?" → 출력 색
      │
      ▼
Blending / Depth    ← 기존 화면과 어떻게 합칠지. (진화 2의 additive가 여기)
      │
      ▼
화면 (framebuffer)
```

핵심 감각 세 개:

- **두 셰이더는 실행 빈도가 다르다.** vertex는 점 개수만큼(1000개면 1000번), fragment는 **rasterization이 만든 fragment 수만큼**이다. 파티클이 겹쳐 그려지면(overdraw) 한 픽셀 위에서 fragment가 여러 번 실행돼 최종 픽셀 수를 훌쩍 넘는다 — 진화 2의 additive 블렌딩이 바로 이 겹침을 대량으로 만든다. 비용이 어디서 터지는지의 기초.
- **가운데 rasterization은 네 것이 아니다.** GPU가 알아서 도형을 픽셀로 쪼갠다. 너는 "어디에(vertex)"와 "무슨 색(fragment)"만 정한다.
- **`gl.POINTS`는 특수 케이스다.** 점 하나가 `gl_PointSize` 픽셀짜리 정사각형으로 부풀고, fragment shader에서 `gl_PointCoord`(그 사각형 안 0~1 좌표)로 원을 그려 파낸다. 진화 2에서 "사각형이 아닌 발광점"을 만드는 게 이 원리다.

## 3. 좌표 공간: -1 ~ +1 이라는 약속

vertex shader가 출력하는 `gl_Position`은 **clip space** 좌표(vec4)다. 여기서 두 공간을 구분해야 한다 — 진화 3·4에서 원근·카메라를 만나면 이 구분이 결정적이 된다:

- **clip space**: `gl_Position`이 사는 4D 동차좌표. 가시 범위는 `-w ≤ x, y, z ≤ w`.
- **NDC**(normalized device coordinates): GPU가 clip space를 `w`로 나눈 뒤(perspective divide)의 좌표. **여기서 화면 = x, y가 -1 ~ +1인 정사각형**이 된다. 왼쪽아래 `(-1,-1)`, 오른쪽위 `(+1,+1)`, 중앙 `(0,0)`.

파이프라인이 이 NDC를 다시 화면 픽셀로 변환한다(viewport transform). 픽셀도 미터도 아닌 **캔버스 크기와 무관한 정규화 좌표**라 리사이즈해도 셰이더는 안 바뀐다.

> **진화 1에선 w=1이라 clip space와 NDC가 수치상 같다.** 그래서 `gl_Position`에 그냥 -1~1로 써도 된다. w가 실제로 일하는 건 원근이 등장할 때 — 진화 3에서 three.js의 카메라/projection이 이 w를 채운다. 지금은 **"-1~1로 생각하되, 그게 정확히는 w로 나눈 뒤의 NDC이고 w=1이라 같아 보이는 것"** 정도만 알아두면 된다.

## 4. 병렬성 모델: "같은 프로그램을 N번 동시에"

셰이더의 정체는 **"수천~수백만 개 데이터에 똑같이 적용되는 작은 프로그램"** 이다. GPU가 이 프로그램을 여러 개 동시에(SIMD식) 굴린다. 여기서 오는 규칙들:

- **실행끼리 서로 못 본다.** 정점 5번 셰이더는 정점 4번의 결과를 모른다. 각자 독립. (이 격리가 진화 4에서 깨진다 — compute + storage buffer는 서로의 데이터를 읽는다. 그게 시뮬레이션을 가능케 함.)
- **`print`가 없다.** 수천 개가 동시에 도는데 콘솔이 있을 리 없다. 그래서 **디버깅 = 값을 색으로 출력**한다. 궁금한 값을 색 채널 하나(예: 빨강)에 실어 화면에 찍고, 그 밝기로 값을 읽는다. 이건 요령이 아니라 유일한 창문이다.
- **분기(if)는 공짜가 아니다.** SIMD 특성상 갈래가 갈리면 양쪽을 다 실행하고 버린다. 지금은 "셰이더에서 if 남발은 CPU와 비용 구조가 다르다"만 알아두면 된다.

## 5. 셰이더가 왜 있나 (고정 → 프로그래머블)

옛날 GPU는 "정해진 조명·변환만 하는 고정 회로"였다. 지금 GPU는 파이프라인의 두 칸(vertex·fragment)에 **네 코드를 꽂을 수 있게** 열어놨다. 그래서 "프로그래머블 파이프라인"이다.

파티클이 이걸 배우기 좋은 이유: 파티클의 위치·색·움직임이 전부 그 두 칸에서 결정된다. **파티클 = 셰이더 학습의 순수 표본.** 조명·재질·그림자 같은 곁가지 없이 파이프라인 그 자체만 만진다.

---

## 6. ★ 같은 문제, 4개의 도구 (이 문서의 핵심)

어떤 단일 정본도 이걸 안 이어준다. 각 정본은 자기 도구 하나만 가르치니까. **여기가 우리 문서가 존재하는 이유다.** 같은 파티클 시스템을 4번 만들 때, 사실 바뀌는 건 아래 세 축의 "어디서/무엇으로"뿐이다.

### 축 A — 파티클 데이터는 어디에 사나 (버퍼의 여정)

| 진화       | 데이터가 사는 곳             | 네가 하는 일                                                            |
| ---------- | ---------------------------- | ----------------------------------------------------------------------- |
| 1 WebGL2   | VBO (직접 생성)              | `createBuffer` → `bufferData` → `vertexAttribPointer` 손으로 배선       |
| 2 GLSL     | 같은 VBO                     | 버퍼는 그대로. 셰이더가 그 데이터를 절차적으로 가공                     |
| 3 three.js | `BufferGeometry`의 attribute | **진화 1의 그 버퍼가 이 래퍼 안에 숨어 있다.** `setAttribute`가 곧 배선 |
| 4 WebGPU   | storage buffer               | attribute의 진화형. 이제 compute shader가 **읽고 쓴다**                 |

> three.js에서 `BufferGeometry`를 처음 볼 때 "이게 뭐지"가 아니라 **"아, 진화 1에서 손으로 하던 그 버퍼구나"** 로 보이면 bottom-up이 성공한 거다.

### 축 B — 파티클 움직임(물리)은 어디서 계산되나

| 진화       | 계산 위치                            | 상태 유지 방식                                                          |
| ---------- | ------------------------------------ | ----------------------------------------------------------------------- |
| 1 WebGL2   | 안 움직임 (정적)                     | 없음 — 프레임 루프만 돎                                                 |
| 2 GLSL     | **vertex shader** (시간 기반 절차적) | 무상태(stateless). `u_time`으로 매 프레임 처음부터 재계산               |
| 3 three.js | 여전히 셰이더 (three.js가 감쌈)      | 대개 무상태 유지                                                        |
| 4 WebGPU   | **compute shader**                   | **유상태(stateful).** ping-pong 버퍼로 이전 프레임 속도·위치를 이어받음 |

이 축이 진화 4가 "정점"인 이유를 설명한다. 무상태(2·3)에서 유상태(4)로 넘어가는 순간이 진짜 시뮬레이션의 시작이고, 그게 readback 없이 GPU 안에서 완결된다.

### 축 C — 셰이더 언어와 그 그릇

| 진화       | 언어          | 그릇                                                      |
| ---------- | ------------- | --------------------------------------------------------- |
| 1 WebGL2   | GLSL (최소한) | 원시 program (`gl_Position`/`gl_PointSize`만)             |
| 2 GLSL     | GLSL (주인공) | 같은 program, 이제 노이즈·색·블렌딩이 여기                |
| 3 three.js | **같은 GLSL** | `ShaderMaterial` 안으로 이사. 진화 2 셰이더 재사용        |
| 4 WebGPU   | **WGSL**      | pipeline + bind group. GLSL→WGSL 문법 차이 + compute 추가 |

> ⚠️ "재사용"엔 함정이 있다: three.js `ShaderMaterial`은 `projectionMatrix`·`modelViewMatrix` 같은 uniform과 `position` 등 attribute를 **자동 주입**한다. 진화 2의 raw GLSL(직접 clip space에 쓰던 vertex shader)을 그대로 붙이면 재선언 충돌이 난다 — fragment는 대체로 그대로 오지만, vertex는 three.js 규약에 맞춰 조정하거나 `RawShaderMaterial`을 쓴다. 진화 3에서 다시 만날 함정.

---

## 요약 한 장

- 방향은 **CPU→GPU→화면** (네 readback의 반대).
- 네가 제어하는 건 파이프라인의 두 칸: **vertex(어디에) · fragment(무슨 색)**.
- 좌표는 **-1~+1 clip space**.
- 셰이더는 **같은 프로그램 N개 병렬** — print 없음, 색으로 디버그.
- 4번의 진화는 결국 **데이터가 사는 곳 · 물리가 도는 곳 · 셰이더의 그릇**, 이 세 축이 바뀌는 것뿐이다.
